# Ускорение на видеокарте (W7, ворота G9)

Необязательная библиотека **`libmcgen_cuda`** (CUDA, только NVIDIA) считает на видеокарте то, что окупается, и выдаёт **побитово тот же результат, что CPU**.
Без неё, без драйвера/устройства и при любой ошибке всё работает на CPU как раньше. Спека — `docs/superpowers/specs/2026-10-02-blender-worldgen-addon-design.md` §3.6.

Все числа ниже — **измеренные** на: AMD Ryzen 5 5500 (6 ядер / 12 потоков), RTX 4080 SUPER (16 ГБ, sm_89), драйвер 617.14, CUDA Toolkit 12.0, WSL2.
Машина во время замеров была занята другими процессами (load average 5–27 на 12 потоков), поэтому времена CPU «плавают» и завышены против простоя; там, где это важно,
приведено и процессорное время (`user`), оно от нагрузки зависит слабо.

## 1. Что реализовано и что нет

| Часть | Статус | Примечание |
|---|---|---|
| Сетка биомов `mcgen_biome_grid` (BiomeManager-зум + климат + R-дерево), все версии 26.1–26.4, Overworld (6 пресетов) / Nether / End | **готово, в режиме Auto** | бит-в-бит; 78–150× быстрее CPU (карта 2048²) |
| Рельеф TERRAIN 26.3/26.4: плотность `final_density` + жилы руд на GPU, aquifer и раскладка — CPU | **готово, бит-идентично, но включается только явно (режим GPU)** | область 64×64: стадия TERRAIN — **3,4–3,9× по процессорному времени**, 1,7–2,8× по времени на занятой машине (порог G9 «≥3×» по времени не подтверждён, см. §6) |
| Рельеф 26.1/26.2 (ветка `double`, NoiseChunk с ячейками) | не реализовано | считается на CPU (проверено: дампы совпадают) |
| Карта высот для дальнего LOD на CUDA | не реализовано | см. §9 |
| Меширование, карверы, декорации, постройки, поверхность | на GPU не переносятся (спека §3.6) | |
| AMD (HIP) / Apple / Intel | нет | HIP — портом тех же исходников с повторной проверкой (план) |

## 2. Профиль CPU-конвейера (веха M1)

`mcgen-cli bench` с накопительными масками стадий, 26.3 Overworld `normal`, seed 12345, 12 потоков, процессорное время `user` (с), разности масок:

| стадия | 32×32 чанков, с | доля | 64×64 чанков, с | доля | мс/чанк (64×64) |
|---|---:|---:|---:|---:|---:|
| BIOMES | 0,87 | 2,4 % | 3,4 | 2,7 % | 0,83 |
| TERRAIN (заполнение шумом + жилы + aquifer) | 12,4 | 34,7 % | 47,7 | 37,6 % | 11,6 |
| SURFACE | 8,8 | 24,7 % | 41,4 | 32,7 % | 10,1 |
| CARVERS | 1,4 | 3,9 % | 2,5 | 2,0 % | 0,6 |
| FEATURES | 9,3 | 26,0 % | 19,8 | 15,6 % | 4,8 |
| STRUCTURES + растекание жидкостей | 2,9 | 8,1 % | 11,9 | 9,4 % | 2,9 |
| **всего (0x3f)** | **35,7** | | **126,7** | | **30,9** |

Внутри `terrain_fill_chunk` (callgrind, 12×12 чанков, 1 поток, доли инструкций): объёмный расчёт `final_density` — **52 %**, aquifer (`aq_substance`) — 22 %,
жилы руд — 20 % (почти всё — те же объёмные расчёты плотности/богатства жил), `aq_init` — 2 %, цикл по блокам — 4 %.
Вывод: сквозное время сцены определяют SURFACE и TERRAIN; стадия TERRAIN — единственная крупная однородная и массово-параллельная; биомы и карта биомов дают наибольший выигрыш на порядки.

## 3. Устройство

```
libmcgen (C)                                         libmcgen_cuda (CUDA, отдельный файл)
  mcgen_biome_grid ──► gpu_bridge.c ─ dlopen ───────►  mcgpu_biome.cu   сетка биомов (ядра, R-дерево, зум)
  terrain_fill_chunk ─► (служба пакетов региона) ───►  mcgpu_terrain.cu плотность + жилы пакетами по чанкам
  gpu_export_new.inc / gpu_export_old.inc               mcgpu_dev.cuh     шум, точечные вычислители, сплайны
   (экспорт скомпилированных программ)                  mcgpu_core.cu     устройства, инициализация, ошибки
```

* **ABI** (`libmcgen/gpu/mcgen_gpu_abi.h`, `MCGPU_ABI`): плоские POD-структуры — программа density-функций (узлы, таблицы октав шума `McgOct`, слои, сплайны), узлы R-дерева биомов,
  описание мира. `libmcgen_cuda` **не линкуется с libmcgen**: ядро выгружает в неё данные, она их считает.
* **Мост** (`src/gpu_bridge.c/.h`): динамическая загрузка (`dlopen`/`LoadLibrary`), поиск библиотеки: `mcgen_gpu_set_library_path`, `MCGEN_CUDA_LIB`, каталог самой libmcgen, системные пути.
  Экспортёры `gpu_export_new.inc` / `gpu_export_old.inc` подключены в конец `df_new.c` / `df_old.c` (нужны приватные типы дерева сэмплеров `S` и графа `ON`).
* **Программы вместо жёсткого кода.** GPU получает не «формулы ванили», а скомпилированные деревья density-функций самого мира: поддерживаются все пресеты, тонкие настройки и любые
  версии автоматически; таблицы перестановок октав берутся из уже созданных CPU-шумов (инициализация RNG на GPU не нужна). Узлы с неподдержанными видами (`log`, `pow`, `round`, `find_top_surface` в климате…)
  не выгружаются — мир остаётся на CPU с причиной в статусе.
* **Биомы.** Точечный вычислитель программы (ветка float 26.3+ и ветка double 26.1/26.2, срезы `slice` «запечены» в контекст узлов), порядок вычислений и ленивость не меняют значения (функции чистые);
  `BiomeManager.getBiome` (SHA-256 сида, фиддл, 8 кандидатов) и `Climate.RTree` с теми же правилами «ничьих», что `world_biome_cell` (цепочка по порядку заполнения секции).
  Точка, которую GPU не может решить строго как CPU (NaN в климате, цепочка ничьих >12) помечается и пересчитывается на CPU (13 точек из 16·10⁶).
  End считается по таблице чанков (один расчёт островов на чанк).
* **Рельеф (26.3+).** Исполнитель повторяет рекурсию `s_volume`: для каждого узла и объёма — ядро поэлементной арифметики с теми же формулами и порядком операций, что у CPU
  (`add_volume_impl` шума, `interp_fill_cell`, спайны по буферам координат, `K_SLICE_*`, Beardifier — значения считает CPU по обратному вызову). Один план годится для любого чанка (объёмы заданы относительно чанка);
  пакет — до 64 чанков (арена видеопамяти 1,6 ГБ для Overworld). Жилы руд: правила `ore_vein` решаются на GPU для каждой позиции (Xoroshiro, «щель» — точечный вычислитель); CPU применяет «заплатку» к блокам,
  которые после aquifer оказались не воздухом и не жидкостью.
* **Состояние кэшей CPU.** Точечные запросы aquifer (`s_value(exclusion…)`) попадают в ячейки кэшей, которые на CPU оставляет `s_volume(final_density)` (значения объёмного пути отличаются от точечного в последних битах).
  Чтобы результат не зависел от того, кто считал плотность, GPU возвращает содержимое **тех ячеек кэшей, что нужны aquifer**, а по трассе порядка посещений (с ленивостью координат сплайнов: ядро отмечает использованные
  координаты) определяет, какую ячейку CPU оставил бы; CPU вставляет их в свой контекст (`gpu_sctx_set_cell`). Чанк, для которого состояние определить нельзя, считается на CPU целиком.
* **Служба пакетов региона.** `generate_region` запускает поток-производитель: он по плану (чанки региона + кольцо гало для растекания жидкостей) считает пакеты на GPU в закреплённую память (4 слота), рабочие потоки CPU берут
  готовые данные своего чанка (`terrain_fill_chunk`) и делают aquifer/раскладку. При отказе GPU чанк считается на CPU.

## 4. Бит-точность

* `nvcc --fmad=false`, `-prec-div=true -prec-sqrt=true -ftz=false`, без fast-math; хост-код `-ffp-contract=off`; Windows — `/fp:strict`. 64-битные целые для Xoroshiro, SHA-256, LCG зума.
* Те же численные ветки, что у CPU: `double` (26.1/26.2: `old_normal_get`, `wrap_old`, `noise_d`) и `float` (26.3+: `NoiseStack`, `gn_perlin_get_f`, объёмный путь `add_volume_impl` с **другим** порядком сложения градиентов, чем у точечного).
* Исполнение через PTX (вперёд-совместимость, `CUDA_FORCE_PTX_JIT=1`) даёт то же самое (проверено: 1,6·10⁶ точек биомов и 192 чанка рельефа, 0 расхождений).
* Самопроверка: при первом использовании мира сравниваются 384 случайные точки GPU и CPU (результат кэшируется в мире; при расхождении мир остаётся на CPU, причина в статусе);
  `mcgen_gpu_selftest(McGen*, n)` — тестовые миры версии (Overworld ×3 пресета, Nether, End × 2 seed). Режим Auto не использует GPU, если самопроверка провалена.

## 6. Скорость (измерено)

**Карта биомов 2048×2048, шаг 4 блока** (`tests/g9_bench --biome 2048`; минимум из 3 повторов; GPU эксклюзивно под `flock /tmp/gpu.lock`; load average CPU при замере 19–27, поэтому времена CPU завышены):

| версия | Overworld CPU → GPU | Nether CPU → GPU | End CPU → GPU |
|---|---|---|---|
| 26.1 | 11,56 с → 0,120 с (**96×**) | 0,62 с → 0,023 с (27×) | 9,23 с → 0,079 с (117×) |
| 26.2 | 11,50 с → 0,119 с (**96×**) | 0,67 с → 0,023 с (29×) | 5,78 с → 0,074 с (78×) |
| 26.3 | 7,89 с → 0,053 с (**150×**) | 0,34 с → 0,009 с (37×) | 6,48 с → 0,074 с (88×) |
| 26.4-snapshot-2 | 4,88 с → 0,045 с (**108×**) | 0,38 с → 0,009 с (42×) | 7,16 с → 0,083 с (87×) |

(при меньшей нагрузке: 26.3 Overworld 6,87 с → 0,047 с = 146×; 1024² — 1,92 с → 0,012 с = 156×). Результаты CPU и GPU в каждом замере идентичны. GPU-путь включает копирование результата.

**TERRAIN, область 64×64 чанков, стадии BIOMES|TERRAIN, 26.3 Overworld** (`mcgen-cli bench --nx 64 --nz 64 --stages 3 --threads 12`; 5 чередующихся пар; в GPU-замере есть 0,5 с одноразовой инициализации CUDA):

| | время, с | процессорное время `user`, с |
|---|---|---|
| CPU | 8,4 – 12,3 | 50,2 – 54,0 |
| GPU (рельеф плотность + жилы) | 4,2 – 5,6 | 16,3 – 17,1 |
| отношение (по парам) | **1,8 – 2,3×** | **2,9 – 3,3×** |

**Только стадия TERRAIN** (`--stages 2`, 4 чередующиеся пары, load average 31–35 — машина была занята другими процессами сильнее обычного):

| | время, с | процессорное время `user`, с |
|---|---|---|
| CPU | 10,8 – 20,0 | 51,0 – 54,8 |
| GPU | 5,1 – 8,2 | 14,2 – 15,9 |
| отношение (по парам) | 1,7 – 2,8× | **3,4 – 3,9×** |

Без растекания жидкостей (`tests/g9_bench --terrain 64`, `fluid_flow = 0`, минимум из 3): 1,5 – 2,0× по времени. На уровне объёмов (без aquifer и раскладки) GPU считает плотность+жилы Overworld ≈ 1 300–2 000 чанков/с
(Nether ≈ 11 000, End ≈ 27 000 чанков/с) против ≈ 250 чанков/с (4 мс/чанк на объёмы) одного ядра CPU.

Остаток на CPU после переноса плотности и жил (≈ 3,5–4 мс/чанк): aquifer (≈ 2,4–2,8 мс/чанк — основной вклад), биомы чанка (0,8), `aq_init`, копирование. Ускорение по времени ограничено этой CPU-частью, одноразовой инициализацией CUDA
(≈ 0,5 с на процесс) и последовательным кольцом гало для растекания жидкостей (260 чанков при 64×64: по измеренной стоимости чанка это порядка секунды и на CPU, и на GPU).

**Критерий G9 для TERRAIN («≥3× на 64×64»).** По процессорному времени стадии он **выполнен** (3,4–3,9×); по времени (wall) на занятой машине — **не подтверждён** (1,7–2,8×; на свободной машине замерить не удалось).
Поэтому рельеф на GPU **оставлен явным режимом «GPU»** (он освобождает ≈ 2/3 процессорного времени — интерфейс Blender остаётся отзывчивым — и побитово тот же), а в режиме **Auto** на GPU считаются только биомы
(`mcgen_gpu_set_features` / `MCGEN_GPU_AUTO_TERRAIN=1` включают рельеф в Auto). Включить рельеф в Auto по умолчанию стоит после замера wall-времени на свободной машине.

## 7. Использование

**C-API** (`include/mcgen.h`): `mcgen_gpu_device_count/info`, `mcgen_gpu_set_compute(MCGEN_COMPUTE_CPU|GPU|AUTO, device)`, `mcgen_gpu_get_compute`, `mcgen_gpu_set_features(MCGEN_GPU_BIOMES|MCGEN_GPU_TERRAIN)`,
`mcgen_gpu_status(buf, n)` (строки «ключ: значение»: mode, state, features, device, library, worlds_ok/failed, last_fallback, selftest, reason), `mcgen_gpu_selftest(McGen*, n, report, len)`,
`mcgen_gpu_biome_grid` / `mcgen_biome_grid_cpu` (строго GPU / строго CPU), `mcgen_gpu_biome_points`. `mcgen_biome_grid` сама выбирает путь (Auto: сетки ≥ 16 384 точек, GPU готов и проверен).

**Что считает видеокарта в режиме Auto (аддон, `core/gpu.py`):** карты биомов — всегда, когда GPU готов и самопроверка не провалена; **рельеф — для областей от 256 чанков (16×16)** (`AUTO_TERRAIN_MIN_CHUNKS`; измерено на RTX 4080 SUPER, стадия 0x3, 12 потоков CPU, включая запуск процесса: 8×8 — CPU 0,62 с против GPU 0,80 с, 16×16 — 1,50 против 1,08 с, 32×32 — 3,71 против 2,60 с). Меньшие области быстрее на процессоре: у GPU есть постоянные накладные расходы на описание мира. В режиме **GPU** (View ▸ Compute) рельеф считается на видеокарте всегда. Панель Stats показывает строку «GPU считает: …».

**Переменные окружения** (CLI, тесты): `MCGEN_COMPUTE=cpu|gpu|auto`, `MCGEN_CUDA_LIB=<файл>`, `MCGEN_GPU_AUTO_TERRAIN=1`, `MCGEN_GPU_DEBUG=1` (сообщения моста: время описания мира, занятость GPU, ожидания),
`MCGPU_PROFILE=1` (время ядер по видам узлов и фазам пакета, размеры арены).

**Аддон Blender** (`core/gpu.py`, `ui/`): вкладка View — «Compute: Auto / CPU / GPU (имя карты)»; Stats — блок «Compute»: режим, устройство, результат самопроверки, причина возврата на CPU,
кнопки «GPU Self-test» и «GPU Benchmark» (карта биомов 2048² и рельеф 64×64: CPU / GPU / идентичность / ускорение). Режим сцены применяется перед каждым запуском генерации. Без библиотеки или устройства блок показывает причину;
всё работает на CPU. Самопроверка выполняется при первом бенчмарке/по кнопке; в Auto GPU не используется, если она провалена.

**Как отключить:** режим «CPU» в интерфейсе; `MCGEN_COMPUTE=cpu`; не класть `libmcgen_cuda` (удалить файл рядом с libmcgen); `mcgen_gpu_set_compute(MCGEN_COMPUTE_CPU, -1)`.

## 8. Сборка и поставка

* **Linux:** `libmcgen/gpu/build.sh` (nvcc ≥ 12; по умолчанию `sm_89` + PTX `compute_75` для вперёд-совместимости → `libmcgen/build/gpu/libmcgen_cuda.so`; `CUDA_ARCH="75 80 86 89" libmcgen/gpu/build.sh` — несколько
  архитектур, ≈ 10 МБ; `--install` копирует в `blender/mcgen_addon/lib/linux-x64/`). cudart и libstdc++ слинкованы статически, экспорт — только `mcgpu_*` (`mcgpu.map`); нужен лишь драйвер NVIDIA. Цель `make -C libmcgen gpu`.
* **Windows:** кнопка **Build GPU library** в аддоне (Stats ▸ Compute) собирает `mcgen_cuda.dll` на машине пользователя его nvcc — `core/gpu_build.py`: ищет nvcc (`PATH`, `CUDA_PATH`, `Program Files\NVIDIA GPU Computing Toolkit\CUDA\v*`),
  `vcvars64.bat` Visual Studio / Build Tools (через `vswhere`), определяет архитектуру по `nvidia-smi --query-gpu=compute_cap` (только то, что умеет этот nvcc; для более новых карт — PTX `compute_75`), собирает теми же флагами, что `build.sh`
  (`--fmad=false`, без fast-math; хост — `/fp:strict /MT /EHsc`), кладёт результат в `<кэш аддона>\gpu\mcgen_cuda.dll` и подключает через `mcgen_gpu_set_library_path`; при «unsupported Visual Studio version» повторяет с `-allow-unsupported-compiler`.
  Исходники для этого лежат в пакете аддона (`gpu_src/libmcgen/gpu` + `gpu_src/engine/{mc_rng,mc_common}.h`, кладёт `tools/build_extension.py`). Вручную: `libmcgen\gpu\build.bat` в «x64 Native Tools Command Prompt» (сам находит vcvars, если `cl` нет в PATH, и архитектуру по `nvidia-smi`).
  **Бинарник для Windows в этой среде собрать нельзя** (нет MSVC; nvcc не кросс-компилирует под Windows), поэтому путь Windows **не проверялся на живой машине** — проверены Linux-ветка той же функции (настоящая сборка + загрузка + самопроверка), построение командной строки/`.bat` и разбор вывода `nvidia-smi`; при сбое на Windows диагностика — `<кэш>\gpu\build.log`.
  Бит-точность гарантирует не компилятор, а самопроверка «GPU = CPU» в аддоне (в Auto GPU без неё не используется).
* `tools/build_extension.py`: всё, что лежит в `blender/mcgen_addon/lib/<платформа>/`, попадает в zip платформы, т. е. `libmcgen_cuda` — необязательный файл рядом с `libmcgen`; для macOS/Intel его нет (CUDA недоступна).
* Остальная сборка не затронута: `libmcgen/build.py` (zig) собирает `gpu_bridge.c` как обычный исходник (динамическая загрузка; на Windows — без `-ldl`).

## 9. Ограничения и план

* Только NVIDIA/CUDA. Версии: биомы — все; рельеф — 26.3+ (26.1/26.2 — CPU).
* Перенос aquifer на GPU (оценка по профилю: основной остаток CPU) требует воспроизведения кэш-семантики точечных запросов (`find_top_surface`, попадания в ячейки) — большой объём работы; вместе со слиянием мелких ядер
  объёмного исполнителя (около 800 запусков на пакет) и переносом биомов чанка (объёмный путь `sampleVolume` + цепочка ничьих) мог бы довести ускорение TERRAIN до ≥ 3× по времени.
* Карта высот для дальнего LOD на GPU не делалась: LOD аддона строится по уже сгенерированным чанкам (`mesh/lod.py`); вычислитель объёмов исполнителя для неё пригоден (объём с шагом ячейки + интерполяция по y).
* Растекание жидкостей: кольцо гало чанков вокруг области генерируется последовательно (как и на CPU) — это часть времени при включённом `fluid_flow`.
* HIP (AMD): порт исходников `gpu/*.cu` с повторным прогоном `tests/g9_*`.

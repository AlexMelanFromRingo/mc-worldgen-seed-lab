# Недетерминизм генерации декораций (FEATURES) в 26.x: причины и воспроизведение

Документ отвечает на вопрос «почему два прогона настоящего сервера на одном seed дают разные миры и можно ли довести libmcgen до 100 %».
Все числа получены на ванильном сервере 26.3 (seed 8675309, 12345, −7048155917072976836; область r = 6 чанков, `variant=features`/`full`),
инструменты — `tools/gt/` (JFR, Java-агент, `replay_check.py`, `light_check.py`).

## 1. Масштаб: сама игра не воспроизводима

Два прогона одного и того же мира (центральная область 9×9 чанков, 7 962 624 блока):

| пара | расхождений | совпадение |
|---|---:|---:|
| ag3 ↔ ag4 | 11 208 | 99,859 % |
| ag4 ↔ ag5 | 18 781 | 99,764 % |
| ag5 ↔ ag6 | 17 206 | 99,784 % |
| ag6 ↔ ag7 | 16 380 | 99,794 % |
| libmcgen (порядок по умолчанию) ↔ ag4 | 14 266 | 99,821 % |
| libmcgen (типичный порядок прогонов без ag4) ↔ ag4 | 11 502 | 99,856 % |
| libmcgen (**записанный порядок ag4**) ↔ ag4 | **1** | **99,99999 %** |

То есть порядок по умолчанию уже неотличим от «ещё одного прогона игры»; 100 % против произвольного прогона недостижимы по определению,
но **любой конкретный прогон воспроизводится точно**, если известны его расписание (порядок шагов FEATURES и момент готовности света/соседей).

## 1a. Предел для любого детерминированного генератора (12 прогонов одного мира, область 9×9 чанков, 7 962 624 блока)

* Клеток, где 12 прогонов настоящего сервера не согласны между собой: **44 027 (0,55 %)**.
* Лучший возможный фиксированный ответ — поклеточное большинство 12 прогонов — расходится с отдельным прогоном в среднем на **9 661** клетку (от 5 150 до 14 379).
* Порядок по умолчанию (модель планировщика) расходится с отдельным прогоном в среднем на 16 372 клетки (старый обход «x, z» — 16 208), с поклеточным большинством — на 10 967; два прогона игры между собой — 11–19 тыс.
  То есть порядок по умолчанию неотличим от «ещё одного прогона игры», а до теоретического пола осталось ≈ 1,7×.
* Игру нельзя сделать детерминированной настройкой: с `-Dmax.bg.threads=1` два прогона всё равно расходятся (3 727 и 5 517 клеток; порядок шагов различается у 3,9 % пар) — остальные потоки (главный, световой) вмешиваются по времени.
* Поэтому «100 % против произвольного прогона» не определено: у игры нет единственного ответа. Определено «100 % против записанного прогона» — оно достигнуто (0 расхождений из 16,6 млн блоков на 10 из 11 прогонов Overworld и на Nether).

## 2. Причины

### 2.1 Порядок шагов FEATURES (главная)
`ChunkMap`/`ChunkGenerationTask`/`ChunkTaskDispatcher` (исходники 26.3: `server/level`, `world/level/chunk/status`):

* Для каждого чанка области создаётся задача до статуса FULL (кольца r+1, r+2 — FULL, r+3 — INITIALIZE_LIGHT, r+4 — TERRAIN, …; уровень билета forceload 31 + расстояние).
* Задача идёт по слоям статусов; на слое FEATURES она **для всех чанков 3×3 вокруг себя** (x внешний, z внутренний) вызывает `applyStep`. Первая задача, дошедшая до чанка, выполняет его шаг; остальные ждут его future.
  Отсюда характерный порядок: сначала блок 3×3, затем «полосы по 3» вдоль z, чередующиеся с полосами соседних задач.
* Шаги FEATURES/STRUCTURE_* выполняются **синхронно** в одном последовательном исполнителе `worldgen` (по одному чанку за раз, очередь `ChunkTaskPriorityQueue`:
  сначала меньший уровень билета, внутри уровня — порядок вставки ключа чанка). Шаги BIOMES и TERRAIN — асинхронные (`Util.backgroundExecutor`).
  Когда задача снова готова (завершился TERRAIN соседей), она возвращается в хвост очереди своего уровня → порядок «кто следующий» определяется гонкой завершений TERRAIN.
* Порядок создания самих задач идёт из `DistanceManager.chunksToUpdateFutures` — это `ReferenceOpenHashSet<ChunkHolder>`, то есть порядок обхода зависит от identity-хэшей объектов (произвольная, но для одной JVM почти повторяемая перестановка).

**Модель планировщика** (`tools/gt/sched_sim.py`, точный порт зависимостей `ChunkStep`/`ChunkLevel`): воспроизводит число шагов по статусам у настоящего сервера
(STRUCTURE_STARTS 1521 = 39², BIOMES 529 = 23², TERRAIN 441 = 21², FEATURES 361 = 19², FULL 289 = 17² при области r = 6) и характерный порядок «блок 3×3, затем полосы по 3».
Расхождение порядка пар соседних чанков с записанными прогонами: у наивного «x, затем z» — 19,1 %, у модели (создание задач в порядке x, z; без разброса асинхронных задержек) — 9,2 %,
между самими прогонами игры — 4,6 %. Порядок создания задач в игре определяет обход `ReferenceOpenHashSet` (случайные порядки модель описывает хуже: ≥ 16 %), остаток — кольца уровней 32/33,
чьи задачи в игре вклиниваются раньше, чем в модели. **Порядок по умолчанию в libmcgen — эта модель** (`libmcgen/src/feature_sched.c`, порт `sched_sim.py`; `MCGEN_FEATURES_SCHED=xz` возвращает прежний обход «x, затем z»;
`MCGEN_FEATURES_ORDER_OUT=файл` записывает использованный порядок). Параллельность не нарушает воспроизводимости: чанк идёт после всех более ранних чанков порядка,
чьи окна 3×3 пересекаются с его окном, независимые чанки обрабатываются параллельно (тест `libmcgen/tests/g5_sched_order.py`: порядок C = Python, 1 поток = 4 потока).
Эффект на эталонах G5 (стабильные клетки, область r = 10): Nether seed 12345 — 26 925 → 6 340 расхождений, суммарно по шести строкам Overworld/Nether — 99 115 → 78 532 (−21 %);
на Overworld seed 8675309 хуже (18,9 → 22,8 тыс.), на других нейтрально. Относительно записанных прогонов (r = 6): Nether −6 %, Overworld ±1 %, то есть в пределах шума игры (11–19 тыс. между прогонами).
Полный G5/G6 (строго, с кольцами r+1…r+2): 12/12 PASS, раньше Nether seed 12345 давал 99,859 % (FAIL).

Измерение: между прогонами порядок отличается у 4–5 % пар соседних чанков (≤ 2 по Чебышёву), у порядка «x, затем z» относительно прогонов — у 19 %.
JFR-событие `minecraft.ChunkGeneration` (включается `tools/gt/jfr/chunkgen.jfc`) даёт точный порядок шагов; перекрытий по времени у шагов FEATURES нет (0).

### 2.2 Свет, видимый во время FEATURES (грибы)
`MushroomBlock.canSurvive` читает `getRawBrightness(pos, 0)` из `ThreadedLevelLightEngine` без ожидания. Выяснено (исходники `world/level/lighting`, проверено агентом):

* читается **видимая** копия данных (`SkyLightSectionStorage.getLightValue(.., updating=false)`);
* секция света «хранит» данные, если непустая секция блоков есть у неё или у любого из 26 соседей и чанк-владелец уже прошёл `INITIALIZE_LIGHT`
  (`LayerLightSectionStorage.updateSectionStatus`: счётчик соседей); слой — нули; колонка выше самой верхней такой секции даёт 15;
* ещё не освещённые и не зарегистрированные колонки дают 15, зарегистрированные — 0 ⇒ гриб ставится (`< 13`);
* внутри окна 3×3 вокруг декорируемого чанка настоящего (ненулевого) света ещё нет: `LIGHT` любого из 8 соседей требует `INITIALIZE_LIGHT` центра.

Какие чанки уже «видны» к началу шага — гонка со световым потоком: чанк, декорированный на 1 шаг раньше, виден в 12 % случаев, на 2 — в 45 %, на 3 — в 70 %, на 9+ — всегда.
Реализовано в `fc_sky_light` (`libmcgen/src/feature_region.c`); маска «видимых» чанков 5×5 берётся из JFR (третье поле строки порядка) либо из лага в шагах (`MCGEN_FEATURES_INITLAG`, по умолчанию 3).

### 2.3 Пост-обработка при FULL (`LevelChunk.postProcessGeneration`)
Для каждой помеченной позиции игра вызывает `FluidState.tick` и `Block.updateFromNeighbourShapes` (флаги записи 276):

* грибы — `MushroomBlock.updateShape` → `canSurvive` с **настоящей** яркостью `max(блочный, небесный)` (≥ 13 ⇒ воздух): `light_raw_final` (`libmcgen/src/light.c`);
  небо — источники `y ≥ lowestSourceY`, затухание `max(1, lightDampening)`; блочный свет — свечение блока минус то же затухание (в Nether — лава, светокамень, грибной свет).
  Обе модели сверены с `SkyLight`/`BlockLight`, сохранёнными игрой в чанках (`tools/gt/light_check.py [--block]`: 0 расхождений на 60 чанках 5 миров Overworld и на 5 чанках Nether);
* прочие растения (`VegetationBlock.updateShape`) исчезают, если почву заменили диски (`DiskFeature.markAboveForPostProcessing`) или деревья;
* `MultifaceBlock` (светящийся лишайник) теряет грани без опоры;
* деревья вызывают `StructureTemplate.updateShapeAtEdge` для **любых** соседних растений (двойные цветы, трава на изменённой почве), а не только для лоз и какао;
* жидкости: форма блока при растекании — `Shapes.mergedFaceOccludes` по граням; блоки с пустой формой (растения, лишайник, ковры сбоку) жидкость пропускают;
  `FluidState` берётся из настоящих классов (морская трава, ламинария — источники воды).

## 3. Что реализовано в libmcgen

| компонент | файл |
|---|---|
| порядок шагов «из файла» + маска видимости света | `feature.c` (`MCGEN_FEATURES_SEQ=file`, `MCGEN_FEATURES_ORDER`, `MCGEN_FEATURES_RING=3`) |
| порядок пост-обработки жидкостей | `region.c` (`MCGEN_FLUID_ORDER`) |
| свет при FEATURES | `feature_region.c` (`fc_sky_light`, `fc_init_mask`, `fc_snapshot_sections`) |
| свет при FULL (небо) | `light.c` (`light_sky_final`) |
| `updateShape` в пост-обработке и на краях деревьев | `structure_post.c` (общий `update_shape`, `structure_update_shape_fc`) |
| затухание света, форма света в `block_flags.json` | `tests/g5_blockflags/BlockFlags.java` (`damp`, `lshape`) |
| форма при растекании жидкостей | `fluidpp.c` (`face_full`, `fluid_of` по `BsTab.fluid`) |

Формат файла порядка: строки `cx cz [маска]`, маска — шестнадцатеричные 25 бит окна 5×5 вокруг чанка (бит `(dz+2)*5+dx+2`: чанк уже прошёл INITIALIZE_LIGHT к началу шага).

## 5. Как воспроизвести конкретный прогон игры

```bash
# 1) прогон сервера с JFR и (необязательно) агентом отладки
MCGEN_GT_JVM_EXTRA="-XX:StartFlightRecording=filename=run/gt/jfr_x.jfr,settings=tools/gt/jfr/chunkgen.jfc,dumponexit=true" \
  python3 tools/gt/gen_world.py --version 26.3 --variant features --dim overworld --seed 8675309 --cx 0 --cz 0 --radius 6 --tag x --force
# 2) воспроизведение: порядок шагов + маски света + порядок пост-обработки жидкостей → сравнение
python3 tools/gt/replay_check.py run/gt/26.3/features/overworld-s8675309-c0_0-r6_x run/gt/jfr_x.jfr --default-too
```

Отладка конкретной клетки в игре: `tools/gt/agent` (Java-агент; `-Ddbg.watch="x,y,z;…"` — все записи в клетки со стеком, `M` — пометки пост-обработки, `K` — записи при FULL;
`-Ddbg.cls=MushroomBlock` — постановки грибов с именем фичи; `canSurvive` грибов с яркостью). Сборка: `tools/gt/agent/build.sh` (JDK 24+).

## 6. Что осталось

* Две клетки в b4 (джунгли): лоза и какао у блока, срезанного озером лавы после дерева; в игре они убраны (воздух), у нас остались.
  Причина не воспроизведена в повторном прогоне (порядок там другой); логика `updateShape` на краях деревьев и пост-обработки подключена, но звено, убирающее эти блоки, не найдено.
* Блочный свет при FEATURES и тонкая полоса света от уже освещённых внешних чанков при FEATURES не моделируются (внутри окна 3×3 света ещё нет; при FULL оба вида света считаются полностью).
* Порядок по умолчанию — «типичный», а не предсказуемый: предсказать порядок конкретного прогона нельзя (гонка потоков, порядок хэшей), можно только записать.

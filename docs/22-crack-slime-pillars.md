## 1. Итоги

1. **Формулы слайм-чанков, башен Края и шахт одинаковы в 26.1, 26.2, 26.3.** Исходники `WorldgenRandom`, `SingleThreadedRandomSource`, `BitRandomSource`, `LegacyRandomSource`, `RandomSpreadType`, `RandomSource` побайтно
   идентичны; тела `EndSpikeFeature.getSpikesForLevel` и `SpikeCacheLoader.load` (md5) и `Util.toShuffledList(IntStream,…)` — идентичны (в `EndSpikeFeature` различается лишь оболочка Feature/Config). Реальный код игры (oracle)
   даёт бит-в-бит одинаковые карты слайм-чанков (12 карт 128×128 и 2 карты 512×512) и 60 раскладок башен во всех трёх версиях. Различие версий — только набор `abandoned_camp` (26.3).
2. **Слайм: реализован аналитический алгоритм** — старшие 13 бит seed находятся в замкнутом виде (§3.2); совпадает с перебором 2^30 бит-в-бит (40 случайных конфигураций × GPU/CPU + данные oracle). Время: 1.2–2.5 мс (GPU) /
   30 мс (CPU, 12 потоков) для N ≥ 12 положительных чанков; 6 мс / 0.25 с для N=10; 0.13 с / 3.3 с для N=6 (4.9·10^8 кандидатов). Перебор 2^30 (на GPU 0.2–5 с при N=8…16, на CPU до 86 с при N=14) остаётся для `--max-errors > 0` и как эталон.
3. **Оценка «≥ 15 положительных чанков» — нижняя граница информации, но не достаточное условие.** Слайм-карта имеет *почти-симметрии* (seed'ы `W + j·2^35` и родственные семейства дают одну карту, кроме чанков у границы переполнения),
   поэтому число ложных кандидатов убывает примерно как 10^3–10^4/N, а не как 2^48·10^-N: N=16 → 3 928 (мед.), 30 → 184, 200 → 15, 1000 → 6. Единственность даёт полная карта слайм/не-слайм (128×128 → 1, 96×96 → 2, 64×64 → 6) или
   любые независимые ≈ 15–20 бит (2–3 структуры, башни, `--int32`, `--suggest`).
4. **Башни Края:** pillar key по 10 высотам за ~2 мс; 2^32 seed ключа фильтруются предикатами: с lifting — 3 мс на процесс (GPU) / 1 мс (CPU), полный 2^32 без lifting — 35 мс ядро (GPU) / 2.4–3.5 с (CPU).
5. **Шахты:** 7.97 бит на стартовый чанк (нужно ≥ 6–7); lifting невозможен → полный перебор 2^48: ядро 1.64–1.75·10^11 W/с (стабильно на 2^34…2^42) ⇒ **≈ 29 мин на GPU** (экстраполяция; единым прогоном 2^48 **не подтверждено**,
   §5.3); с liftable-структурами (`--with-structs`) — 0.3–0.7 с на весь процесс.
6. **Проверено против реального кода (oracle):** 713 проверок по трём версиям (212+24, 212+24, 217+24) — 0 провалов; плюс 40 случайных конфигураций «аналитика == перебор» и самопроверки ядер (§7).

## 2. Общее

* Слайм-чанки, башни Края, placement структур и шахты зависят только от `seed mod 2^48` (`LegacyRandomSource`; docs/01 §1, §5.3). Проверено oracle: `seed` и `seed ^ (0xABCD<<48)` дают одинаковые карты и башни.
  Старшие 16 бит — из другого источника (hashed seed, биомы, декораторы; docs/13 §2). `--expand-random`: если мир создан автосидом (`RandomSource.create().nextLong()`), по 48 битам старшие 16 определяются (≈ 1 вариант;
  проверено oracle на seed'ах вида `nextLong(LCG(x))`). `--int32`: оставить только seed, влезающие в int32 (набранное число, `String.hashCode()`: биты 32..47 все 0 или 1) — убирает почти все ложные кандидаты.
* **Файл наблюдений структур** (`--with-structs`; общий для трёх инструментов): строки `<structure_set>;<chunkX>;<chunkZ>` (также пробелы; регистр, `minecraft:` и `struct ` не важны), `slime;cx;cz;0|1`, `#` — комментарий.
  Имя — id набора из `data/structure_sets-<V>.json` (`desert_pyramids`, `villages`, `end_cities`, `mineshafts`, …), id структуры (`desert_pyramid`, `end_city`) или единственное число. Параметры placement (spacing/separation/salt/
  spread_type/frequency/reducer) берутся из JSON (`--version`, `--data-dir`, `--sets`), иначе из встроенной таблицы. Поддержан `random_spread` (linear/triangular, reducers `default`, `legacy_type_1/2/3`). Проверяется **необходимое** условие
  (потенциальный чанк + reducer): `exclusion_zone` и биомы не проверяются — кандидатов может быть больше, чем в игре, истинный seed не теряется.
* **Сверка placement с oracle:** `crack-pillars --scan-set S SET cx0 cz0 nx nz` == oracle `structs <dim> S SET …` точно для 16 наборов overworld (в т.ч. triangular `ocean_monuments`/`woodland_mansions`, reducers `buried_treasures` [legacy_type_2],
  `mineshafts` [legacy_type_3], `pillager_outposts` [legacy_type_1: oracle ⊆ моё, лишние — в радиусе 10 чанков от потенциальной деревни = exclusion_zone]), `abandoned_camp` (26.3), `end_cities`, Nether-наборы: 5 seed × 3 версии, 0 расхождений.
* Lifting: `nextInt(lim)` при `lim = 2^k·odd` даёт k младших бит `r = next(31)` (биты 17.. состояния), зависящие лишь от младших 17+k бит `W` ⇒ необходимое условие на младшие L ≤ 20 бит. Используется в слайме (бит 17), башнях и шахтах.

## 3. crack-slime

### 3.1 Формула (проверена по коду трёх версий и по oracle)
```
WorldgenRandom.seedSlimeChunk(x, z, seed, salt) = SingleThreadedRandomSource( seed + x*x*4987142 + x*5947611 + z*z*4392871L + z*389711 ^ salt )
slime chunk  <=>  seedSlimeChunk(chunkX, chunkZ, levelSeed, 987234911L).nextInt(10) == 0
```
`WorldgenRandom.java:71-73` (идентичен в 26.1/26.2/26.3); использование: 26.2/26.3 `world/entity/monster/cubemob/Slime.java:93`, 26.1 `world/entity/monster/Slime.java:291` (`random.nextInt(10) == 0 && slimeChunk && pos.getY() < 40`).
`x*x*4987142`, `x*5947611`, `z*389711` — `int` с переполнением (затем знаковое расширение), `z*z` — `int`, лишь потом `* 4392871L`; сложение слева направо, затем `^ salt`. В `mc.h`: `s0 = ((W + c(x,z)) mod 2^48) ^ salt ^ 0x5DEECE66D`,
`W = seed mod 2^48`. `nextInt(10)`: `bits = next(31); val = bits % 10`, повтор при `bits - val + 9 < 0` (т.е. `bits ≥ 2147483640`, вероятность 3.7·10^-9 — учтено точным путём). Карты 128×128 (12 seed на версию) и 512×512 (2 seed) == oracle `slime`.

### 3.2 Алгоритмы
**Общее — lifting по чётности.** Слайм ⇒ `r = next(31)` чётно ⇒ бит 17 состояния `s1 = s0·M + B` равен 0 ⇒ зависит лишь от младших 18 бит `W`; каждый положительный чанк отсекает половину из 2^18 «низов» `l`.

**`--algo brute`** (классический, нужен при `--max-errors > 0`): для каждого выжившего низа перебрать 2^30 старших бит, проверка `r % 10 == 0` с ранним выходом. Стоимость `nlows·2^30` (`nlows ≈ 2^18/2^N`, на практике больше — низы коррелируют).

**`--algo analytic`** (по умолчанию при `--max-errors 0`): `W = l + (m<<18) + (g<<35)`; `l` — из lifting, `m` (17 бит) перебирается, `g` (13 бит) находится аналитически. XOR с константой `KX = salt ^ M < 2^35` не затрагивает биты ≥ 35, поэтому
старшие 13 бит `W + c` входят в `s1` аддитивно. Для чанка с `c = cl + (ch<<35)`:
```
v = l + (m<<18) + cl;  A = ((v mod 2^35 ^ KX)·M + B) mod 2^48;  a = A>>17;  e = ch + (v>>35);  d = e·M mod 2^13;  T = g·M mod 2^13
r = (a + 2^18·((T+d) mod 2^13)) mod 2^31 = ρ + 2^18·j,   ρ = (a + 2^18·d) mod 2^18,   j = (T + β) mod 2^13,   β = (a + 2^18·d)>>18      (2^18·2^13 = 2^31)
r ≡ 0 (mod 10)  <=>  ρ чётно  и  j ≡ ρ (mod 5)                                         (2^18 ≡ 4 mod 10)
```
Для разных чанков `j_k = (j_1 + D_k) mod 8192`, `D_k = β_k − β_1`; так как `8192 ≡ 2 (mod 5)`, условие чанка `k`: `q = (λ_1 + D_k − λ_k) mod 5 ∈ {0, 2}` (`q = 0` ⇒ `j_1 < 8192 − D_k`; `q = 2` ⇒ `j_1 ≥ 8192 − D_k`; иначе пара `(l,m)` отвергнута).
Итог: `j_1 ∈ [lo, hi)`, `j_1 ≡ λ_1 (mod 5)` ⇒ все `g` выписываются явно; кандидаты проверяются точно (отрицательные чанки, предикаты, зона отклонения `r ≥ 2147483640` идёт точным путём). Работа: `nlows·2^17` пар
(в 8192 раза меньше, чем brute), на пару — ~2 чанка (согласие двух чанков с вероятностью 2/5). Эталон на Python: `proto_slime_analytic.py` (совпал с brute: 126 кандидатов при N=30, 718 при N=24).

### 3.3 Почти-симметрии: почему «15 чанков» не хватает
Ложные кандидаты — не случайный мусор: `D = W' − W` почти всегда кратно 2^29, а сдвиг `r_k' − r_k` одинаков для всех чанков. Точный механизм — семейство `D = j·2^35`: `r' = (r + m·2^18) mod 2^31`, `m = j·M mod 2^13`.
Чанк остаётся слайм-чанком, если без переполнения `m ≡ 0 (mod 5)` и `m < 8192·(1 − r_max/2^31)`, либо у всех чанков переполнение, `m ≡ 2 (mod 5)` и `m ≥ 8192·(1 − r_min/2^31)`. Пример (30 положительных; r_max/2^31 = 0.9887, r_min/2^31 = 0.0641):
18 + 105 = 123 ложных seed'а в этом семействе — ровно столько нашёл прямой перебор семейства. В среднем семейство даёт ≈ 3277/(N+1) ложных seed'ов, остальные (D кратно 2^29…2^34) увеличивают итог ≈ в 4 раза. Оценка `2^48·10^-N` верна, пока доминируют случайные
кандидаты (N ≤ 8: измерено 4.9·10^8, 2.3·10^7, 4.0·10^6 против 2.8·10^8, 2.8·10^7, 2.8·10^6), с N ≈ 9–10 доминируют семейства.

**Сколько наблюдений нужно (измерено, окно 128×128, медианы по 4–8 seed'ам):** только положительные — N=16 → 3 928 кандидатов, 30 → 184, 60 → 38, 200 → 15, 1000 → 6 (единственности нет). Полная карта слайм/не-слайм (положительные + отрицательные):
16×16 → 39, 32×32 → 14, 64×64 → 6, 96×96 → 2, 128×128 → 1 (1–3). 30 положительных + 1000 отрицательных → 16, + 3000 → 8. Практически: ≥ 20–30 положительных (≈ 10^2–10^3 кандидатов за миллисекунды) + независимые данные
(2–3 структуры/башни: 6 структур + карта 32×32 → 1 кандидат) либо полная карта ≥ 96×96. Меньше ~12 положительных — выдача бессмысленна (инструмент отказывается при ожидаемых > 5·10^7 кандидатов, `--force` отменяет). `--suggest K` подбирает
ещё не наблюдённые чанки, делящие кандидатов пополам (эксперимент: 166 → 83 → 42 → 22 → 10 → 4 → 3 за 6 проверок; остаток различается лишь на редких чанках у границы переполнения).

## 4. crack-pillars

### 4.1 Механика (`EndSpikeFeature`, одинакова в 26.1/26.2/26.3)

Наблюдаются: **высота** (Y блока бедрока под кристаллом, 76…103 шаг 3) — её читает SeedcrackerX (`EndPillarsFinder`: 10 `BedrockMarkerFinder`, `PillarData(heights)` — **в порядке индексов**; `PillarData.test` перебирает 2^16 pillar seed'ов с

`--heights 97,?,91,r2,cage,…` (`?` — неизвестно, `rN` — радиус, `cage`/`nocage`).

### 4.2 Алгоритм
**Шаг 1.** Перебор 2^16 ключей, сравнение масок допустимых size (~2 мс). 65 090 различных раскладок из 65 536 ключей ⇒ у 891 ключа (1.36 %) раскладка неоднозначна — шаг 2 выполняется для всех совпавших ключей. По oracle (10 seed × 3 версии): только радиусы → 3–8 ключей,
только клетки → ≈ 1450 (больше `--max-keys 64`), 6 из 10 высот → 1–2.
**Шаг 2.** `nextLong() & 65535` = биты 16..31 второго состояния `s2 = s0·M² + B(M+1)`; зависит лишь от младших 32 бит `W`: для ключа K множество младших 32 бит — аффинная биекция от 16 свободных бит `x`
(`s0_lo32 = ((K<<16|x) − C2)·M2^-1 mod 2^32`, `W_lo32 = s0_lo32 ^ 0x5DEECE66D`), старшие 16 бит свободны ⇒ **ровно 2^32 seed на ключ** (то же множество, что у `TimeMachine`). Перебор `2^16 × 2^16` с предикатами `--with-structs`;
**lifting** по младшим 20 битам заранее отсекает `x` (liftable-структуры, положительные слайм-чанки). Без предикатов: `--list N`, `--count-only`; `--candidates файл` — проверить список. Отказ при > 5·10^7 ожидаемых кандидатов на ключ (`--force`).

## 5. crack-mineshaft

### 5.1 Механика
Набор `mineshafts`: `random_spread` spacing 1 / separation 0 (каждый чанк — свой регион), `frequency 0.004`, `legacy_type_3`: `setLargeFeatureSeed(seed, cx, cz); nextDouble() < (double)0.004F`
(26.3 `AbstractSpreadingStructurePlacement.java:107-111`, 26.1/26.2 `StructurePlacement.java:110`); `MineshaftStructure.findGenerationPoint` вызывает ещё `context.random().nextDouble()` — на размещение не влияет. `(double)0.004F = 0.0040000001899…` учтено
точно (целочисленный порог `v53 ≤ 36028798730239`). Стартовый чанк — чанк главной комнаты (`MineshaftStructure.generatePiecesAndAdjust` → `MineShaftRoom(…, getBlockX(2), getBlockZ(2))`, `MineshaftPieces.java:960-967`): её северо-западный угол
в блоке `(16cx+2, 16cz+2)`. 7.97 бит на чанк: 6 чанков = 47.8 бит (≈ 1.15 ложных), 7 — 55.8.

### 5.2 Алгоритм
`nextDouble()` берёт старшие биты второго состояния, зависящего от всех 48 бит (`t1 = LCG(scramble(r)) < 0.004·2^48`, `r = cx·a ^ cz·b ^ W`, `a`,`b` — два `nextLong`); в отличие от слайма старшие биты идут через XOR и умножение `cx·a` ⇒ замкнутого решения и lifting нет ⇒
**полный перебор 2^48** с ранним выходом: `ms_fast` (32-битная арифметика: 4 шага LCG, два умножения 48×48, порог `t1>>22 ≤ 268435` отсекает 99.6 %), остальные предикаты — для выживших. С liftable-предикатами из `--with-structs` — lifting (L ≤ 20) и объём 2^28…2^30.
`--range BASE,BITS` — только `[BASE, BASE+2^BITS)`; отказ при < 6 шахтах без `--force`; `--progress`.

### 5.3 Замеры (под `flock`, лучшее из 3; ядро после прогрева)
| диапазон | время, с | W/с |
|---|---|---|
| 2^34 | 0.098 | 1.75·10^11 |
| 2^36 | 0.410 | 1.68·10^11 |
| 2^38 | 1.66 | 1.65·10^11 |
| 2^40 | 6.68 | 1.65·10^11 |
| 2^42 (1 прогон) | 26.9 | 1.64·10^11 |
| CPU 12 потоков 2^28 / 2^30 | 0.42 / 1.69 | 6.3·10^8 |

Экстраполяция на 2^48 (2.815·10^14): **≈ 1.7·10^3 с ≈ 29 мин на GPU**, ≈ 5 суток на 12 потоках CPU (непрактично без lifting). **Единым прогоном 2^48 не подтверждено:** запуск 2026-09-30 при сторонней загрузке GPU (скорость 4·10^10…1·10^11 W/с) завершился на ≈ 36 %
(`Elapsed 30:17`) без итоговых строк — причина не установлена (код возврата тогда не сохранялся; скрипт `run_mineshaft_full.sh` дополнен), лог `results/mineshaft-full.txt`. Корректность проверена на диапазонах (истинный seed найден в 2^36 вокруг seed для 3 версий × 4 seed) и полным
пространством с lifting: 8 шахт + 4 liftable-структуры из oracle → 1 кандидат за 0.27–0.72 с на процесс (3 версии × 4 seed).

### 5.4 Запуск
```

crack/bin/crack-mineshaft mines.txt --with-structs structs.txt        # + liftable-структуры: секунды
crack/bin/crack-mineshaft mines.txt --range 123456789012345,36        # частичный перебор / тест
```

## 8. Ограничения
1. **Слайм.** Нужны реальные слайм-чанки: в болотах (y 51–70) спавн по другому правилу, слаймы из спавнеров/разделения не связаны с чанком; отсутствие слаймов — слабое свидетельство (0.152 бит); полные карты без знания seed недоступны (нужен мод/таблица). По одним положительным
   чанкам единственности практически нет (§3.3) — результат есть семейство кандидатов. `--max-errors > 0` — только brute (секунды–минуты при малом N). Выдача > 4·10^6 кандидатов усекается буфером (счётчик точный). В brute предфильтр младших бит пренебрегает отклонением `nextInt` (4·10^-9 на чанк).
2. **Башни.** Нужны высоты (или радиусы/клетки) по индексам раскладки; неоднозначные ключи (1.36 %) обрабатываются перебором. Без дополнительных предикатов 2^32 seed ключа можно лишь перечислить — нужно ≈ 32 бита структур/слайм-чанков.
3. **Шахты.** Без liftable-предикатов — полный 2^48 (≈ 29 мин GPU по экстраполяции; прогон целиком не подтверждён); CPU непрактичен. Стартовый чанк надо знать точно (угол главной комнаты `(16cx+2, 16cz+2)`); окно «около шахты» не реализовано.
4. **Структуры:** только random_spread; `exclusion_zone` и биомы не проверяются (необходимое условие). Strongholds/End-острова/бедрок — другие инструменты (docs/13).
5. Не реализовано: аналитика для `--max-errors > 0`; 64-битное продолжение (кроме `--expand-random`, `--int32`).

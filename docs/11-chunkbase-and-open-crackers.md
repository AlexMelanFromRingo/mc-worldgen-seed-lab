## 0. Главные выводы (коротко)

1. **Chunkbase не является крэкером.** Все его приложения требуют известный seed, кроме «Seed Finder» (прямой перебор seed по условиям на биомы/структуры) и старого «Seed Finder for Slime Chunks» (2014, MC 1.8). Подтверждено текстом FAQ и прямым запуском. [П]
2. **Клиент chunkbase — Rust-WASM (wasm-bindgen), не cubiomes-C.** Один общий модуль `as6TbD-hInKU.simd.wasm` (520 616 байт) + не-SIMD fallback (505 475 байт), пул Web Worker (Comlink). Упоминаний cubiomes на сайте нет (страница лицензий содержит только NPM-пакеты). [П по файлам/заголовкам; «независимая реализация, не порт cubiomes» — В]. PROJECT.md называет chunkbase «портом cubiomes-подобного кода» — это не подтверждается.
3. **Chunkbase уже поддерживает 26.1, 26.2, 26.3 (Java), Bedrock 26.0–26.52, а также экспериментальные Java 26.4 и Bedrock 26.60.** [П: список версий прямо из `<select>` страницы].
4. **Публичные крэкеры для 26.x существуют и живы:** SeedcrackerX (мод; 26.1 — 2026-03-25, 26.2 — 2026-06-20, 26.3 — 2026-09-29), `someone12469/seed-cracking` (Overworld bedrock + переход камень/глубинный сланец + жилы руды -> полный 64-бит seed; релизы 26.1, 26.2, 26.3), `Alist2930/MCBE-seedcracker` (Bedrock Edition). [П]
5. **Основные «узкие места» для 26.x:** структуры, слайм-чанки, шипы Края, лут/деревья — всё на Java LCG (48 бит, «структурный seed»); биомы/шум/декорации/бедрок — на Xoroshiro128++ от полного 64-битного seed. По Xoroshiro публичного быстрого обращения «seed -> ограничения» нет: организаторы Minecraft@Home прямо пишут, что лучший известный метод — полный перебор 2^64, baseline 580 млрд seed/с на RTX 5090 (~1 год). [П: repos/pseudogravity_xoroshiro/bounties/problem2-xsetseed/README.md]
6. **Слайм-чанки:** известная атака — 2^18 (бит чётности next(31)) + 2^30; минимум ~15 «положительных» слайм-чанков по информации, практически 18–30 (см. §B1). GPU-реализации именно *восстановления по наблюдениям* не найдено; найденные CUDA-проекты делают *прямой* поиск кластеров. [Н для GPU-крэка]
7. **Замеры сторонних GPU-проектов на ближайшем к нашему железу** (RTX 4080 / 4080 SUPER): JUNO (26.3) ~10.4 млрд индексов/с общий скан, гейт 40 млрд/с; double-Perlin 16 октав 2553 М/с на 4080 (tall_sugar_cane). См. §B9.
8. **Внимание для кросс-проверки:** в `xpple/cubiomes` (форк с MC_26_1..MC_26_3) ветвления по `MC_26_3` есть только в таблицах дерева биомов, конфигах структур и списке биомов; в коде шума/`biomenoise.c` отдельной float-логики 26.3 нет. [П: grep по repos/xpple_cubiomes] Это не доказывает ошибку, но значит, что форк нельзя считать эталоном для 26.3 без сверки с oracle.

  **Замер нами** (Chromium headless в WSL2, 12 логических потоков; условие «Village within 128 m in any biome», Java 26.3): ~105 seeds/s в начале, итог **236 seeds/s**, 1.3K просканировано за ~6 с, 50 найдено. [П как наблюдение; это условие только структура+биом-проверка]
- **Seed Finder for Slime Chunks** (https://www.chunkbase.com/apps/seed-finder-slimes, «Last Update: Nov 14, 2014 (MC 1.8)»): пользователь отмечает слайм/не-слайм чанки на карте -> показывает «1 in N seeds» и «Est.» время, искать на N воркерах (JS, без wasm). Это *единственный* «крэкер по наблюдениям» у chunkbase. Наблюдение: после 5/10/14/20 кликов оценка 1 in 100k / 10G / 100T / 100E seeds (то есть ≈10^n: считает только 10^-1 на слайм-чанк). Алгоритма 2^18+2^30 у них нет (линейный перебор) — практически применим только для 1.8 и очень малого числа условий. [В по оценке из UI]

### B1. Слайм-чанки

**Формула (26.3, сверено с src/dec/26.3):** `WorldgenRandom.seedSlimeChunk(x,z,seed,salt=987234911L)` = `RandomSource.createThreadLocalInstance(seed + x*x*4987142 + x*5947611 + z*z*4392871L + z*389711 ^ salt)`; в `Slime.java`: слайм-чанк ⇔ `nextInt(10)==0`, спавн только при `random.nextInt(10)==0 && slimeChunk && pos.getY() < 40`. `SingleThreadedRandomSource` = Java LCG 48 бит (0x5DEECE66D, +11). Формула идентична Minecraft Wiki https://minecraft.wiki/w/Slime (там же: «only the lowest 48 bits of the world seed affect slime chunks»; в Bedrock слайм-чанки **не зависят от seed**, алгоритм другой — MT19937, реверс protolambda/jocopa3 по credits chunkbase). [П]

Следствия [Р + подтверждено источниками ниже]:
- Информация о seed: только **нижние 48 бит** (верхние 16 бит нужны из другого источника: hashed seed, биомы...).
- `nextInt(10)==0` ⇔ `next(31) % 10 == 0` ⇔ (чётно) и (кратно 5). Чётность `next(31)` = бит 17 состояния после одного шага LCG; он зависит **только от нижних 18 бит** (seed+chunkval)^const. Поэтому каждый положительный слайм-чанк — 1 бит-фильтр над 2^18 кандидатов, а потом 2^30 старших бит проверяются полным условием.

Инструменты «наблюдения -> seed»:

1. **pruby/slime-seed** — https://github.com/pruby/slime-seed | C (+Ragel), pthreads | MIT (Copyright 2014 Timothy Goddard) | последний коммит 2018-11-04 | нижние 48 бит seed по **положительным** наблюдениям слайм-чанков (ниже Y=40; отрицательные игнорируются) | `LOWER_BIT_PREFILTER`: перебор 2^18 нижних бит по условию чётности, затем 2^30 верхних × найденные нижние; 32 потока, блоки по 2^23; ранний выход по `required_hits`; `expand48to64random` — разворот 48-бит seed в 64-бит, если seed получен `nextLong()` (2^48 возможных «random seeds») | слайды `presentation/random talk.pdf` [П]: «naive 2^64 ≈ 1800 years», «2^48 ≈ 10 days», «18 bits ≈ 4 ms», «30 confirmed spots -> only one possibility for lower 18 bits, 8 possibilities for lower 48 bits, ~3 seconds to search» | версионно-независим (формула Java) | не развивается.
2. **naryand/seedcrack** (каталог `slime/`) — https://github.com/naryand/seedcrack | C, pthreads (24 потока) | MIT | 2022-05-14 | то же: `findlower18()` (условие next_int_bound(10) чётное) затем `thread30()` (2^30, условие ==0); пример на 22 слайм-чанках (seed 4864391782977103771 в комментарии) [П]. В том же репозитории CUDA/OpenCL-ядра для **диамантовой руды** (`cuda/main.cu`, `opencl/kernel.cl`: декоратор-seed = `(x*a + z*b) ^ seed`, COUNT=4 жил -> seed) и `diorite/`, `ore/` (Java LCG, ≤1.17).
3. **Badel2/slime_seed_finder** — https://github.com/Badel2/slime_seed_finder (web: https://badel2.github.io/slime_seed_finder/) | Rust, WASM-демо | GPL-3.0 | 2024-04-05 | слайм-чанки (+«negative» не-слайм для отсева, допуск ошибок `max_errors`), биомы (≤1.16), дандженсы (Alpha), anvil-сохранения | «we bruteforce 2^18 + 2^30» (docs/slime_chunks.md: «Each slime chunk reduces the expected runtime by 50%, until collisions start to dominate; non-slime chunks don't reduce runtime but remove false positives») | docs/prng.md «Speed» (1 ядро CPU, один `nextInt` 31 бит 2^N раз): 2^24 — 0.113 с; 2^28 — 0.353 с; 2^32 — 4.112 с; 2^36 — 1 мин 04.673 с; 2^40 — 16 мин 42.524 с; «~3 days for 2^48 on one core; multithreaded or modern GPU — a few hours» [П] | seedinfo версии 1.7–1.15 (Java).
4. **chunkbase Seed Finder for Slime Chunks** (см. A5) — линейный перебор, 1.8, JS.

**Оценки минимального числа чанков [Р]:**
- Информация: положительный слайм-чанк = log2(10) = 3.32 бит; не-слайм = -log2(0.9) = 0.152 бит; энтропия случайного чанка H(0.1) = 0.469 бит.
- Только положительные: 48/3.32 = 14.5 -> **15 чанков** дают в среднем 2^48/10^15 = 0.28 ложных кандидата; 16 -> 0.028; 17 -> 0.0028.
- Полная карта (и слайм, и не-слайм): 48/0.469 ≈ **102 чанка** (≈11×11) в теории; алгоритмически без положительных чанков выигрыша от 2^18-трюка нет.
- Трюк 2^18: кандидатов нижних 18 бит ≈ 2^(18-N) при N положительных (N≥18 -> ~1). Наблюдения авторов: 22 чанка — 1 кандидат (naryand), 30 — 1 кандидат (pruby). 
- Работа после трюка: ≈ C18 × 2^30 × 1.25 оценок LCG (для кандидатов с уже чётным next вероятность пройти 1 чанк = 1/5): N=10 -> ~3.4·10^11; N=12 -> 8.6·10^10; N=14 -> 2.1·10^10; N=16 -> 5.4·10^9; N≥18 -> ~1.3–2.7·10^9. Без трюка 2^48 × 1.1 = 3.1·10^14.
- GPU-время [Р, не измерено]: при 1·10^11–4·10^11 оценок LCG/с на RTX 4080 (теоретический потолок по int-пропускной способности ≈ 8·10^11) — N=10 занимает порядка секунд, N≥16 миллисекунды; полный 2^48 без фильтра ≈ 15–50 минут. Для сравнения CPU: Badel2 ~1.1·10^9 вызовов/с на ядро.
- Идея [В, не проверено на слайм]: meet-in-the-middle Matthew Bolan (см. B3) для `nextInt(25)` даёт 2^24+2^24 вместо 2^48; модуль 10 = 2·5 требует адаптации (XOR-константа 0x5e434e432 затрагивает 35 нижних бит).
- «Bit lifting» по `nextInt(bound)` как общий приём описан в Kludwisz/BitLifting (https://github.com/Kludwisz/BitLifting, TeX, 2026-05-17; разделы «Bit lifting using known values of nextInt(bound)», «Combining bit lifting and state prediction»). [П по оглавлению]
- Bedrock: слайм-чанки не содержат информации о seed. [П: minecraft.wiki/w/Slime]

### B3. Hashed seed (SHA-256) [П, сверено с src/dec/26.3]
- `BiomeManager.obfuscateSeed(seed) = Hashing.sha256().hashLong(seed).asLong()` = первые 8 байт SHA-256 от 8-байтного little-endian значения seed (как `WorldSeed.toHash` в https://github.com/SeedFinding/mc_core_java/blob/master/src/main/java/com/seedfinding/mccore/rand/seed/WorldSeed.java). Сервер шлёт это клиенту «since 1.15» (документация кода mc_core); SeedcrackerX 26.3 использует.
- Структурный seed + hashed seed => 2^16 SHA-256, мгновенно. Без структурного seed — перебор 2^64 (необратимая хэш-функция): [Р] hashcat SHA2-256 на RTX 4090 ≈ 22 GH/s (https://gist.github.com/Chick3nman/32e662a5bb63bc4f51b847bb422222fd — 21 975.5 MH/s), 4080 ≈ 0.55–0.6 от 4090 [В] -> полный 2^64 ≈ десятки лет на карту; «random seed» (2^48 значений `nextLong`) ≈ 2^48/(1.2·10^10) ≈ 6 ч на 4080 [Р]. Специализированных GPU-крэкеров hashed seed не найдено [Н].

### B8. Стронгхолды / spawn / eye of ender
- **Код 26.3 (сверено с src/dec/26.3 `ChunkGeneratorStructureState`):** кольца стронгхолдов: `RandomSource.create()` -> `random.setSeed(concentricRingsSeed)` (= seed мира), где `RandomSource.create(long)` = `LegacyRandomSource` (Java LCG). Угол = `nextDouble()*2π`, расстояние = `4*distance + distance*circle*6 + (nextDouble-0.5)*distance*2.5`, затем `findBiomeHorizontal(..., radius 112, ...)` сдвигает позицию к подходящему биому. То есть положение стронгхолдов зависит от нижних 48 бит (+ биомы для сдвига ±112 блоков). [П] Вывод [Р]: точная позиция первого кольца несёт ~до 53 бит (угол) минус потери на сдвиг биомом -> хорошо ложится на решётку с интервальными ограничениями; **готового крэкера «стронгхолды -> seed» не найдено** [Н] (в KaptainWutax/SeedCracker README «Stronghold portal room cracker» остался в списке планов).
- Triangulation по eye of ender (FastStronghold C#, 2026-01; Stronghold-Triangulator Rust; HyperNebula, NexdyMC и т.п.) — определяют позицию стронгхолда **без** seed, к крэку seed не приводят. [П по описаниям репозиториев]
- **spawn:** world spawn определяется по климатическому шуму (в 26.3 `spawnTarget` на density-функциях — PROJECT.md); публичных крэкеров по spawn нет [Н]; chunkbase, cubiomes-viewer (issue #340 «Spawns changed in 1.21.2+») и SeedcrackerZ используют оценку spawn (неточную).
- 12-eye и `mjtb49/StrongholdTrainer` (Java, 2023) / `StrongholdSimulator` — симуляция генерации стронгхолдов/портальных залов (прямые, не крэк).

## F. Рекомендации для проекта (мои выводы)

1. Для крэка *структурного seed* в 26.x полностью хватает Java-LCG-методов (структуры/слайм/шипы/лут) — подход SeedcrackerX/lifting (2^19 -> 2^29) ложится на GPU тривиально; мировой seed — 2^16 проверок hashed seed (SHA-256 первые 8 байт LE) либо биомами.
2. Слайм-чанки: реализовать 2^18+2^30 на CUDA; ожидаемые времена — секунды при ≥10 положительных чанках (оценки в B1, требуют замера).
3. Для не-LCG наблюдаемых (бедрок Overworld, жилы, переход камень/сланец) ориентироваться на `someone12469/seed-cracking` (26.1–26.3) и `pseudogravity/xoroshiro` (bit-sliced, 2^40).
4. Использовать chunkbase только как внешний кросс-чек позиций для 26.x (он обновляется в день релиза и имеет экспериментальную 26.4); не как референс кода и не как источник алгоритмов.
5. Сверять каждое численное утверждение о 26.3 (float-шум) с oracle, а не с `xpple/cubiomes`/JUNO: их шум 26.3 отдельно не моделируется (в JUNO GPU-часть вообще float32 с отсутствием coordinate warp и CPU-перепроверкой).

# 09. «Связанная генерация» (глина → алмазы): почему работало в 1.13–1.17.1 и не работает с 1.18

Тема: пост Reddit «Diamonds and clay linked generation?» (1.16.5, март 2021), приём из ролика Zakviel («найди центр круглого глиняного пятна, отойди на N блоков, копай вниз») и сводка Google «с 1.17+ метод не работает».

**Вывод одной строкой.** Связь была реальной и объясняется арифметикой генератора случайных чисел. С 1.13 по 1.17.1 у каждой фичи свой `java.util.Random` (48-битный LCG) с seed `decorationSeed + index + 10000·step`; seed'ы диска глины и алмазной жилы различаются на малую константу, а LCG у близких seed'ов даёт почти одинаковые старшие биты первых выходов — поэтому x жилы совпадает с x центра диска, а z сдвинут на число, зависящее от биома и от `seed & 15`. С 1.18 генератор Xoroshiro128++ с перемешиванием разрушает корреляцию; в 26.x связи нет.

**Проверено эмпирически на 14 настоящих серверах Mojang 1.7.10 … 1.21.11 и 26.3** (подробно, с таблицами, — [`docs/07`](07-clay-diamond-by-version.md)):

| Версия | Связь «центр диска глины → жила алмаза в том же чанке» |
|---|---|
| 1.7.10, 1.8.9, 1.12.2 | **нет** (140 / 60 / 63 мира): все фичи чанка берут числа из одного последовательного `Random` |
| 1.13.2, 1.14.4 | **только по x**: x жилы = x центра (97,7 %); z не связан, т. к. у алмаза z — **третье** число из `Random` |
| **1.15.2, 1.16.5, 1.17.1** | **по x и по z** — это и есть «трюк» (z жилы = z центра + Δz) |
| 1.18 … 1.21.11, 26.3 | **нет** |

## 1. Что делает код (26.3 прочитан; для старых версий — по данным и воспроизведению ГСЧ)

1. `ChunkGenerator.applyBiomeDecoration` (26.3, строка ~359): `WorldgenRandom random = new WorldgenRandom(new XoroshiroRandomSource(...))`; `decorationSeed = random.setDecorationSeed(worldSeed, chunkOriginX, chunkOriginZ)`: `xScale = nextLong()|1; zScale = nextLong()|1; seed = (chunkX·xScale + chunkZ·zScale) ^ worldSeed`.
2. Для каждой фичи: `random.setFeatureSeed(decorationSeed, index, step)` = `setSeed(decorationSeed + index + 10000·step)`; `index` — индекс фичи в списке биома.
3. Положение фичи в чанке — `in_square`: первые вызовы `nextInt(16)` этого потока (x, затем z).
4. В 1.13–1.17.1 тот же код работает на LCG, в 1.18+ — на Xoroshiro. Индексы глины и алмаза на шаге `UNDERGROUND_ORES` различаются на d = 3 (обычный биом), 2 (болото) в 1.13.2–1.16.5 и 4 / 3 в 1.17.1 (подгонка по реальным мирам, `docs/07` §4.1).

## 2. Арифметика LCG

`java.util.Random`: `S₀ = (seed ^ A) & (2⁴⁸−1)`, `S_{k+1} = S_k·A + 0xB (mod 2⁴⁸)`, `A = 0x5DEECE66D`, `nextInt(16) = S >> 44` (старшие 4 бита).

Для двух фич с seed'ами f_c и f_d разность состояний после k шагов: `Aᵏ·δ' (mod 2⁴⁸)`, где `δ' = (f_c ^ A) − (f_d ^ A)` — малое целое (XOR с `A` меняет разность только через цепочки переносов в младших битах).

| выход | `Aᵏ mod 2⁴⁸ / 2⁴⁴` | следствие |
|---|---|---|
| x (1-е `nextInt`) | A/2⁴⁴ = **0,00143** | при |δ'| < ≈700 x у обеих фич **совпадает** (97,7 % точно, ±1 в 98,8 %) |
| z (2-е `nextInt`) | A² mod 2⁴⁸ = **11,695**·2⁴⁴ | `z_алмаз − z_глина ≡ −11,695·δ' (mod 16)` ± 1 |
| 3-е `nextInt` | A³ mod 2⁴⁸ = **13,29**·2⁴⁴ | у алмаза в 1.13.2/1.14.4 z — **третье** число (порядок x, y, z), у глины — второе ⇒ связи по z нет |

**Почему зависит от seed мира.** Позиция чанка кратна 16 ⇒ младшие 4 бита `decorationSeed` равны `worldSeed & 15` в *каждом* чанке. Они определяют переносы в `δ'`, поэтому Δz — функция в основном от `s0 = worldSeed & 15` и от разности индексов. Пример (1.16.5, s0 = 9, d = 3): δ' = −7 всегда ⇒ −11,695·(−7) = 81,9 ≡ **+2** (наблюдалось +2 в 87 % ячеек). Для s0 = 0: δ' = −3 ⇒ **+3**.

Моделирование (`tools/linked_generation_sim.py`) со случайными 62-битными seed'ами для разных δ даёт **смесь** значений, поэтому моды там слабее (31–59 % для малых δ): в настоящем мире младшие биты фиксированы, и распределение Δz в нём намного концентрированнее (86–92 % у «хороших» s0). Для Xoroshiro модель даёт равномерное распределение (≈0,4–0,5 % на каждую из 256 клеток).

## 3. Точное правило для 1.15.2 – 1.17.1 (из `docs/07`)

* x жилы = x центра диска; z жилы = z центра + Δz (mod 16, внутри чанка); y жилы — третье `nextInt(16)` (0…15, не связан).
* Жила занимает колонки (x_d−1…x_d, z_d−1…z_d): алмаз в каждой с вероятностью ≈ 0,62, хотя бы в одной ≈ 0,79 (фон ≈ 0,02).
* **1.16.5 / 1.15.2, Δz по `seed & 15`:** обычный биом и река: +2 при {1, 9, 13}; +3 при {0, 2, 8, 10, 12, 14}; +4 при {3, 7, 11, 15}; при {4, 5, 6} распределение размазано. Болото: +6 при {1, 2, 9, 10, 13, 14}; −7/+8 при {0, 3, 4, 7, 8, 11, 12, 15}; 0 при {5, 6}.
* **1.17.1:** обычный биом: −1 (78 %) или −2 (22 %) при 12 из 16 значений; болото: от +2 до +4.
* Успех «копай вниз из точки (x_c−1…x_c, z_c+Δz−1)»: 0,37–0,65 для одной колонки, 0,55–0,76 для 2×2 (с учётом границы чанка до 0,82) — для «хороших» s0; для «плохих» миров 0,05–0,25.
* Центры всех «точных» дисков предсказаны воспроизведением ГСЧ без ошибок: 116/116 (1.16.5), 142/142 (1.15.2), 144/144 (1.17.1). Калькулятор — `tools/l3_trick.py`.

## 4. Сравнение с Reddit и Google

* Reddit: «обычный биом: 2 блока к югу; болото: 8 блоков к северу» воспроизводится одновременно при `seed & 15 ∈ {0, 8, 12}` в 1.16.5 (обычный: Δz = +3 ⇒ колонка z_c+2…z_c+3; болото: ±8). «Реки: 2 к северу» воспроизвести **не удалось**: список фич реки совпадает с обычным биомом.
* «После 1.17 не работает»: в 1.17.1 индексы сдвинулись (алмаз 9→11, глина 12→15), и прежнее «+2/+3 к югу» превращается в −1…−2 (север), «старый рецепт» промахивается; с 1.18 связи нет вовсе (Xoroshiro).
* Ролик Zakviel я не смотрел — сопоставление только по правдоподобию.

## 5. Оговорки

* По одному миру для 1.18–1.21.11 и 26.3; 3 / 4 / 10 / 7 миров для 1.14.4 / 1.15.2 / 1.16.5 / 1.17.1; таблицы для остальных `seed & 15` — модель.
* Промежуточные релизы (1.13, 1.13.1, 1.14–1.14.3, 1.15–1.15.1, 1.16–1.16.4, 1.17.0, снапшоты 1.18) не проверялись.
* Индексы фич подогнаны под биомы, попавшиеся в проверенных мирах; для редких биомов ненадёжны. В декомпиляциях только 26.1+, исходники 1.13–1.21.11 не читались.

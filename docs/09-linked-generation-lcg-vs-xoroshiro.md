# 09. «Связанная генерация» (глина → алмазы и т. п.): почему работало до 1.17.1 и не работает с 1.18

Тема: пост Reddit «Diamonds and clay linked generation?» (1.16.5, март 2021), приём «найти глину, отступить на N блоков, копать вниз — там алмазы» (видео Zaquiel / «Заквиэль»), Google-сводка «с 1.17+ метод не работает».

**Вывод одной строкой.** Связь была реальной и объяснима арифметикой генератора случайных чисел: до 1.17.1 декорации чанка брали числа из `java.util.Random` (48-битный LCG), а seed'ы соседних фич в списке биома различаются на малое число (`decorationSeed + index + 10000·step`). У LCG близкие seed'ы дают почти одинаковые верхние биты первых выходов ⇒ «случайные» (x, z) двух фич внутри чанка оказываются почти равны по x и сдвинуты по z на небольшую, зависящую от разницы индексов константу. С 1.18 генератор Xoroshiro128++ с «перемешиванием» (Stafford13) уничтожает эту корреляцию; в 26.x связи нет — это подтверждено и на настоящих чанках 26.3 (`docs/06` §10: пар 177 799 против 184 651 ± 4 769 в контроле).

## 1. Что именно делает код (26.3; в старых версиях то же, но другой тип RNG)

1. `ChunkGenerator.applyBiomeDecoration` (26.3, строка ~359): `WorldgenRandom random = new WorldgenRandom(new XoroshiroRandomSource(...))`; `decorationSeed = random.setDecorationSeed(worldSeed, chunkOriginX, chunkOriginZ)`:
   `xScale = nextLong()|1; zScale = nextLong()|1; seed = (chunkX·xScale + chunkZ·zScale) ^ worldSeed`.
2. Для каждой фичи шага: `random.setFeatureSeed(decorationSeed, index, step)` = `setSeed(decorationSeed + index + 10000·step)`. `index` — глобальный индекс фичи в `FeatureSorter` (порядок по биомам чанка).
3. Положение фичи внутри чанка — модификатор `in_square`: **первые два вызова** `nextInt(16)` из этого же потока: `x = nextInt(16)`, `z = nextInt(16)` (дальше — высота/количество и т. д.). `count` с постоянным числом генератор не расходует.
4. Следовательно, положение глиняного диска и положение алмазной жилы определяются двумя стартовыми seed'ами, различающимися на **δ = разница индексов фич** (в одном шаге; `ore_*` и `disk_*` в 1.16.5 оба в `UNDERGROUND_ORES`, поэтому разница 10000·step отсутствует).

## 2. Арифметика LCG (≤1.17.1)

`java.util.Random`: `state₀ = (seed ^ 0x5DEECE66D) & (2⁴⁸−1)`; `state_{k+1} = state_k·A + 0xB (mod 2⁴⁸)`, `A = 0x5DEECE66D`; `nextInt(16) = (16·(state >> 17)) >> 31`, т. е. определяется **старшими 4 битами** 48-битного состояния.

Два seed'а с разницей δ дают разность состояний после k шагов `Aᵏ·δ mod 2⁴⁸`. Тогда:

| выход | множитель | величина `Aᵏ/2⁴⁴` (сдвиг в клетках 0…16 на единицу δ) |
|---|---|---|
| x (1-й `nextInt`) | A | **0.00143** ⇒ Δx = 0 при |δ| ≲ 700 |
| z (2-й `nextInt`) | A² mod 2⁴⁸ = 205 749 139 540 585 | **11.695** ⇒ Δz ≈ 11.695·δ (mod 16) ± 1 |

(± возникает из-за переносов при `(s+δ) ^ A` против `(s ^ A)+δ`, а также из-за округления вниз.)

Численная модель (`tools/linked_generation_sim.py`, 40–60 тыс. случайных seed'ов на строку; Δ = (позиция второй фичи) − (позиция первой) mod 16):

| δ (разница индексов) | P(Δx = 0), LCG | самое частое Δz и его доля | 3 самых частых Δz вместе | Xoroshiro (любая δ) |
|---|---|---|---|---|
| 1 | 99.1 % | 4 (37 %) | 84 % | равномерно, ≈0.4–0.5 % на каждую из 256 клеток (Δx,Δz) |
| 2 | 98.2 % | 10 (31 %) | 81 % | то же |
| 3 | 97.8 % | 13 (35 %) | 71 % | то же |
| 4 | 96.9 % | 1 (59 %) | 84 % | то же |
| 5 | 96.4 % | 5 (24 %) | 60 % | то же |
| 6 | 95.8 % | 11 (23 %) | 61 % | то же |
| 7 | 95.1 % | 14 (21 %) | 50 % | то же |
| 8 | 94.6 % | 2 (28 %) | 67 % | то же |
| 12 | 92.2 % | 10 (34 %) | 67 % | то же |
| 16 | 90.4 % | 11 (44 %) | 81 % | то же |
| 30 | 85.2 % | 2 (31 %) | 70 % | то же |

Что это значит для игрока:

* **x почти всегда совпадает** (90–99 % при δ ≤ 16), **z сдвинут на 1–3 «типичных» значения, зависящих только от δ** — а δ зависит от **набора фич биома** (чем больше фич добавлено между глиной и алмазом в списке, тем больше δ). Поэтому в Reddit-посте разные биомы дают разные смещения (озёра: 2 к югу; реки: 2 к северу; болота: 8 к северу). Это не «магия биома», а разные δ.
* Сдвиг статистический, а не точный: «80 %+» из поста — типичная доля для малых δ (таблица: топ-3 значения Δz дают 81–84 % при δ = 1, 2, 4, 16).
* Смещение по x/z относительно **начала чанка**; в мировых координатах корректировать нужно уже внутри чанка (диск глины и жила образуются вокруг опорной точки с собственным разбросом).
* С 1.18 (Xoroshiro128++, upgrade seed + `mixStafford13`) распределение (Δx, Δz) равномерно ⇒ метод невозможен, как и сообщает Google-сводка. В 26.3 `WorldgenRandom` — тонкая оболочка над `XoroshiroRandomSource`.

## 3. Статус проверок

* Код: `WorldgenRandom` / `ChunkGenerator.applyBiomeDecoration` / `in_square` — прочитаны в 26.3 (✓).
* Арифметика и таблица — `tools/linked_generation_sim.py` (✓, воспроизводимо).
* Настоящие чанки 26.3: связи нет (✓, `docs/06` §10, контроль сдвигом).
* Эмпирика на старых версиях (1.16.5 / 1.17.1 против 1.18.2 и 1.12–1.15) — отдельная задача, результаты → `docs/07-clay-diamond-by-version.md` (если файл уже появился — смотрите там; пока не подтверждено на настоящем старом сервере).
* Номер версии, с которой исчезла связь, строго следует из типа RNG в `WorldgenRandom`: LCG ≤1.17.1, Xoroshiro ≥1.18 (по памяти о смене RNG при редизайне генерации в 1.18; **точная граница версий не проверена по исходникам старых версий** — в наших декомпиляциях только 26.1+, где `applyBiomeDecoration` создаёт `XoroshiroRandomSource`).

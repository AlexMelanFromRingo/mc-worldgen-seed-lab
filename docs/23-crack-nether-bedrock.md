# 23. crack-nether-bedrock — structure seed по бедроку Незера (CUDA; 26.1 / 26.2 / 26.3)

`crack/bin/crack-nether-bedrock`; исходники `crack/src/nether_bedrock/` (`make -C crack/src/nether_bedrock`, `make cpu` — без CUDA); тесты, данные, замеры — `crack/tests/nether_bedrock/`.
Оригинал — `refs/Nether_Bedrock_Cracker` (Rust), разбор — `docs/12` §1. Машина: RTX 4080 SUPER, Ryzen 5 5500 (6C/12T), общая с другими агентами: чистые замеры сделаны в тихое время, GPU-прогоны — под `flock /tmp/gpu.lock`.

## 0. Итог

* По блокам «бедрок / не бедрок» потолка (y=123..126) и пола (y=1..4) Незера находит **все** совместимые 48-битные structure seed (обычно один, иногда пара «близнецов», §3). Арифметика бедрока в 26.1, 26.2, 26.3 побитово одинакова (§2).
* Полный перебор 2^48 на GPU: **ядро 0.157 с**, «под ключ» **0.43–0.48 с** wall (0.2–0.4 с из них — инициализация CUDA-контекста в WSL2: голая `cudaFree(0)` занимает 0.22–0.38 с). Оригинал, 12 потоков, **простаивающая машина: 59.8 и 63.1 с**
  (под нагрузкой 83–152 с; 151.6 с из задания — из таких). ⇒ ядро ≈ 380× быстрее оригинала (≈ 970× от 151.6 с), «под ключ» ≈ 135× (≈ 330×).
* Хватает ≈ 23 блока-бедрока на y=4/123 по обеим поверхностям (§4). Проверено на реальном коде игры всех трёх версий (§2) и сверено с оригиналом: на 5 файлах наборы seed совпали (включая «близнецов»).

## 1. Использование

`crack-nether-bedrock [опции] <файл | ->`. Вход — строки `x y z bedrock|other` (регистр не важен; без типа = `bedrock`; `#` — комментарий; формат GUI оригинала). Значимы y=1..4 и 123..126 (y=0/127 всегда бедрок, 5..122 — никогда; такие строки
пропускаются), |x|,|z| ≤ 30 000 000; противоречие «и бедрок, и нет» — ошибка. Вывод: structure seed (десятичное, 48 бит) по одному в строке на stdout, `#…` — пояснения, статистика — stderr.
Коды: 0 — готово, 2 — ошибка входа, 3 — ошибка CUDA, 4 — данных недостаточно (отказ / переполнение буфера кандидатов).

| опция | смысл |
|---|---|
| `--version 26.1\|26.2\|26.3` | по умолчанию 26.3 (арифметика одинакова) |
| `--paper1_18` | Paper < 1.19.2-213: в позиционный хэш вместо y идёт 0 (пол) / 122 (потолок), как `BedrockGeneration::Paper1_18` оригинала |
| `--world-seed` | оценка world seed, **верная только для seed, выданного игрой** (`RandomSource.create().nextLong()`, `WorldOptions.java:87-88` / 26.3 `:88-89`); для ручных seed верхние 16 бит — `crack-lift64 --hashed/--biomes` |
| `--cpu`, `--threads N` | счёт на CPU (OpenMP) тем же кодом |
| `--first`, `--check-seed S`, `--filter-seeds FILE` | первый найденный; проверить seed по файлу; отфильтровать список seed |
| `--top-bits K`, `--prefix-start/--prefix-count`, `--kernel 0..4`, `--dense D`, `--bench R` | параметры перебора, вариант ядра, замер ядра |
| `--force`, `--max-cand N` | не отказываться при малой информации; буфер кандидатов (2^24) |
| `--gen S N [bedrock\|mixed]`, `--selftest [gameref-*.txt]` | синтетика по формуле C; самопроверка формул |

Конвейер: `crack-nether-bedrock obs.txt | crack-lift64 --version 26.3 --seeds - [--hashed H]`. Пример: `… data/example_seed_765906787396911863.txt --world-seed` → `13375767216887`, world seed 765906787396911863.

## 2. Формула бедрока и её проверка

Цепочка в коде (`src/dec/<V>/net/minecraft/…`):

| шаг | 26.1 | 26.2 | 26.3 |
|---|---|---|---|
| Незер: `legacy_random_source: true`, `min_y 0`, `height 128` | `data-26.1/…/noise_settings/nether.json:13-16` | `:13-16` | `:74-78` |
| `RandomState.random = LegacyRandomSource(seed).forkPositional()` | `world/level/levelgen/RandomState.java:36` | то же | `:64-66` |
| `getOrCreateRandomFactory(name) = random.fromHashOf(name).forkPositional()`, имя = `minecraft:bedrock_roof/floor` | `RandomState.java:116-117`, `PositionalRandomFactory.java:13-15` | то же | `:124-125` |
| правило | `data/worldgen/SurfaceRuleData.java:301-302` | `:317-318` | `data/minecraft/worldgen/material_rule/bedrock_{floor,roof}.json` |
| условие `blockY<=trueAt→true; >=falseAt→false; p=Mth.map(y,trueAt,falseAt,1,0); nextFloat()<p` | `SurfaceRules.java:735-776` | `:806-850` | `material/condition/VerticalGradientCondition.java:29-46` |
| якоря `aboveBottom/belowTop` | `VerticalAnchor.java:56,90` | `:54,88` | `:75,109` |
| `Mth.getSeed(x,y,z)` | `Mth.java:314-318` | `:332-336` | `:332-336` |

`LegacyRandomSource`, `BitRandomSource.nextLong/nextFloat`, `PositionalRandomFactory` побайтно одинаковы во всех трёх версиях (`diff -q`); различается только устройство правил (26.3: `MaterialRule` в JSON вместо `SurfaceRules`).

```
R       = nextLong(Random(worldSeed))                         (значимы младшие 48 бит)
F_roof  = nextLong(Random(343340730 ^ R)),  F_floor = nextLong(Random(2042456806 ^ R))      (hashCode имён)
state1  = (((Mth.getSeed(x,y,z) ^ F ^ 0x5DEECE66D) mod 2^48)·0x5DEECE66D + 11) mod 2^48,    nextFloat = (state1>>24)·2^-24
пол:     бедрок ⇔ nextFloat < p(y) = (5−y)/5          потолок: бедрок ⇔ !(nextFloat < p(y)), p(y) = (127−y)/5     (top()=127, belowTop(5)=122)
```
Порог точный: `nextFloat < p ⇔ k < T`, `k=state1>>24`, `T=ceil(p·2^24)` = 13421773 / 10066330 / 6710887 / 3355444 для p = .8/.6/.4/.2 (p не кратно 2^-24 ⇒ результат не зависит от округления p).
Наблюдение — **точный интервал** по `state1` (в оригинале приближённый, `f64·MASK48`).

Проверка на реальном коде, три уровня: (1) `gameref-26.{1,2,3}.txt` — 84 значения `nextFloat` реальных `LegacyRandomSource`/фабрик, совпадают с C побитово; (2) `java/NbRef.java` — настоящий `RandomState` с реальными `noise_settings` Незера и
`getOrCreateRandomFactory(Identifier)` — 28 значений совпали; (3) там же **настоящее правило поверхности**: `settings.surfaceRule()` (26.1/26.2) / `settings.materialRule()` (26.3, из `nether.json`) с реальными `SurfaceRules.Context` /
`MaterialRuleContext` (рефлексия, `SurfaceSystem`/`MaterialSystem` из `RandomState`, `WorldGenerationContext` с genDepth 128, minGenY 0), блок — бедрок, если `tryApply` вернул `minecraft:bedrock`. Так проверены весь путь правила и якоря.
7 seed × 6 конфигураций = 42 файла (≈ 2500 блоков, включая |x|,|z| до 29 999 000 — переполнение `int` в `Mth.getSeed`): **для 26.1, 26.2, 26.3 файлы побайтно одинаковы**, формула C согласована со 100 % блоков (`--check-seed`).

## 3. Алгоритм

* **Интервалы.** Блок: `state1 = ((F^h)·M + 11) mod 2^48 ∈ [lo, lo+len)`, `h = (Mth.getSeed ^ 0x5DEECE66D) mod 2^48`, `F` — 48 бит поверхности. `F_roof`, `F_floor` связаны общим `R` ⇒ неизвестное одно.
* **Сверху вниз по старшим битам F** (идея оригинала). Префикс — старшие 48−K бит, K=12 младших неизвестны: `F^h = V + w`, `w<2^K`, `w·M` — дуга шириной `W=(2^K−1)·M` ⇒ префикс допустим лишь при
  `((V·M + 11 − lo + W) mod 2^48) < len + W` (пусто при `len+W ≥ 2^48`). Для слоёв `b=K…0` свои проверки, на слое раскрывается один бит (DFS), при `b=0` проверка точная; проверки по возрастанию `len+W`.
  K=12 оптимален: бедрок при p=.2 даёт `len+W` = 0.567·2^48 (≈ 2.3 проверки на префикс); K=11 — вдвое больше префиксов, K=13 — проверка почти вакуумна (замер §5). Основная — более информативная поверхность.
* **F → R → structure seed.** `F` → `R mod 2^48` обращением `nextLong()` по 48 младшим битам (известны `s2[16..47]` и `s1[16..31]`; перебор 16 бит одним 32-битным сложением на итерацию; ср. 1.225 решения, максимум 2).
  Затем `R →` `F` второй поверхности, точная проверка её блоков; `R → S` тем же обращением; полная проверка всех наблюдений float-формулой игры.
* **Близнецы.** `S ↦ nextLong(Random(S)) mod 2^48` не инъективно: у 22.7 % structure seed (200 000 случайных) есть ровно один близнец с тем же `R`, т.е. с **идентичным** бедроком во всём мире (world seed 0 и 249258135285673; оригинал выдаёт обоих).
  Инструмент печатает оба с пометкой; различать — другими данными (структуры, биомы, `crack-lift64`).
* **GPU.** Ядро верхнего слоя пишет точные `F` основной поверхности через `atomicAdd`; этап A (`k_stageA`, поток на кандидата: обращение `F→R` + вторая поверхность из constant memory) тоже на GPU; на хост идут единицы выживших `R`.
  Проверок в constant memory ≤ 160 на слой (самые селективные; полная проверка на хосте — по всем). Варианты ядра (`--kernel`; **все дают одинаковые кандидаты**, тест [4]), полный проход 2^48 на тихой GPU:

| # | идея | время |
|---|---|---|
| 0 | прямой порт: потоки делят префиксы, ранний выход (расходимость: варп ждёт самую «везучую» линию, 6–7 проверок вместо 2.3) | 0.508 с |
| 1 | «refill»: линия на каждой итерации делает одну проверку, при провале берёт новый префикс; таблица в shared memory | 0.317 с |
| 2 | + 32-битный необходимый фильтр (старшие 32 бита произведения; ложноотрицательных нет — 2.5 млн проверок) | 0.253 с |
| 3 | + DFS в `noinline` | 0.225 с |
| **4** | **Gray-обход групп по 32 префикса**, D=10 плотных проверок (по умолчанию) | **0.157 с** |

  *Gray-обход* (в оригинале нет): в группе `idx=32G+t` значение проверки `= Base + TU[t^hs]`, `TU[u]=(u<<K)·M` аддитивна по битам; при обходе `t` по коду Грея меняется один бит, значение — на `±W_k` (знак известен заранее). Первые D проверок
  для всех 32 префиксов — **одно сложение с константой + `ISETP.AND`** на (префикс, проверка), ≈ 2 команды вместо ≈ 20; работа со старшими 32 битами, ошибка переносов ≤ 32·2^16 перекрыта смещением порога (фильтр необходимый).
  Остальные проверки — только для выживших. D=2/4/6/8/10 → 0.275/0.208/0.169/0.166/0.157 с (при D ≥ 16 хуже: кэш команд). Предел — целочисленная пропускная способность (≈ 23 команды на префикс).

## 4. Сколько блоков нужно

Информация наблюдения — `−log2(len/2^48)`; несут **редкие** исходы: 2.32 бита — бедрок на полу y=4 / потолке y=123 и «не бедрок» на полу y=1 / потолке y=126; 1.32 — бедрок y=3/124, не бедрок y=2/125; 0.74 — бедрок y=2/125, не бедрок y=3/124;
0.32 — бедрок y=1/126, не бедрок y=4/123. Нужно ≥ 48 бит суммарно; основная поверхность должна нести ≳ 25 бит (иначе кандидатов F десятки миллионов: отказ, код 4, без `--force`). Истинный `F` окружён «облаком» F', отличающихся в младших
8–10 битах и тоже удовлетворяющих интервалам (у примера оригинала 153 кандидата F при ожидаемом 10⁻⁸); после `F→R` они отсекаются второй поверхностью. Кандидатов F в 1–50 раз больше наивных `2^(48−I)`.

Эмпирика (`stats.sh`, 16 наборов на N из случайных 48-битных seed, формула C; «ложный» = seed с другим `R`, чем у истинного; близнецы не считаются):

| режим | N | бит | истинный найден | без ложных | ср. ложных | медиана кандидатов F |
|---|---|---|---|---|---|---|
| только бедрок на y=4/123, пол:потолок = 1:1 | 20 | 46.4 | 16/16 | 2/16 | 3.06 | 3.3·10⁶ |
| | 21 | 48.8 | 16/16 | 7/16 | 0.75 | 1.1·10⁶ |
| | 22 | 51.1 | 16/16 | 14/16 | 0.19 | 6.9·10⁵ |
| | 23 | 53.4 | 16/16 | **16/16** | 0 | 1.4·10⁵ |
| | 24 / 30 / 40 / 60 | 56 / 70 / 93 / 139 | 16/16 | 16/16 | 0 | 6.4·10⁴ / 1.4·10³ / 131 / 83 |
| случайные позиции (бедрок и нет), y=4/123 | 60 | 44.3 | 16/16 | 3/16 | 153 | 4.3·10⁶ |
| | 80 / 100 / 150 | 60 / 69 / 110 | 16/16 | 16/16 | 0 | 3.1·10⁴ / 1.8·10³ / 118 |

Порог ≈ 48 бит + 3–5 бит запаса: **22–23 блока-бедрока на y=4/123** (поровну по полу и потолку) либо ≈ 80 случайных позиций (0.72 бита на позицию). Близнецы — в ≈ 20 % запусков.

## 5. Скорость (`results/bench.txt`, `results/crosscheck_orig.txt`)

Методика: ядро GPU — `--bench R` (100–200 повторов по 2^26 префиксов, событие CUDA вокруг ядра, ×1024), под `flock /tmp/gpu.lock`, машина тихая (медиана ≈ min ±5 %). Оригинал — `orig_bench` (обёртка над `bedrock_cracker` без изменений,
профиль как `release-opt` автора: LTO, codegen-units=1), пример `seed 765906787396911863` (36 блоков), 12 потоков. На загруженной машине (loadavg 20–27) время оригинала 83–152 с, GPU «под ключ» растягивался до 1.6 с и больше — это свойство общей машины.

| метод, полный проход 2^48, пример оригинала | время | замечание |
|---|---|---|
| Rust-оригинал, 12 потоков | **59.8 и 63.1 с** | user 585–598 с (8.6 нс/префикс·поток); 1 поток: 5.7–6.5 нс/префикс |
| моя CPU-версия (OpenMP, 12 потоков) | 112–115 с | user 795–820 с; 1 поток: 8.6–9.2 нс/префикс — по CPU-времени в ≈ 1.4× хуже оригинала (запасной путь/тесты) |
| **GPU, ядро 4** | **0.157 с** | 4.4·10¹¹ префиксов/с; ≈ 380× к оригиналу |
| **GPU «под ключ»** | **0.43–0.48 с** wall (первый холодный запуск 0.83 с) | скан 0.15 с + этап A/B 0.01 с + ≈ 0.25 с запуск/CUDA-контекст |
| GPU, ядро 0 (прямой порт) | 0.508 с | |

K=9/10/11/12/13 (ядро 4): 0.91 / 0.46 / 0.24 / **0.156** / 1.0 с. Время ядра почти не зависит от данных (0.15–0.3 с на наших файлах; больше при очень малой информации: миллионы кандидатов, этап A на 1.2·10⁶ кандидатов — доли секунды).

## 6. Тесты (`run_tests.sh`, 21 проверка, ≈ 1.5 мин; логи в `$NB_OUT`)

1. `--selftest`: M·M⁻¹=1; `hashCode`; пороги T(y); 84+28 значений `nextFloat` побитово; обращение `nextLong` (20 000); интервал ≡ float-сравнение на 200 000 блоков (координаты ±30 млн, оба режима y); слой b — необходимое условие (b=0..13);
   слой 0 ≡ точная проверка (300 000); 32-битный фильтр без ложноотрицательных (2.5 млн).
2. Примеры оригинала: `seed 765906787396911863` → 13375767216887 (+ world seed); `old paper` с `--paper1_18` → 240328292736404 (+ −8788534344520786540); без `--paper1_18` не находится.
3. 42 файла реальной игры: истинный seed найден в каждом, близнецов 18, ложных 0. 4. CPU ≡ GPU (окна вокруг истинного префикса, границы не кратные 32, диапазон 2^30); ядра 0–4, D=2..10, K=10..13 — один набор seed.
5. Ввод (противоречия, нет значимых y, мало данных → код 4, версии), `--filter-seeds`, `--first`. 6. Сверка с оригиналом (`crosscheck_orig.sh`, полные проходы Rust): 3 наших файла + 2 примера — наборы seed совпали, в т.ч. пара (0, 249258135285673).
Перегенерация данных реальной игрой: `NB_REGEN=1 run_tests.sh` (`gen_data.sh`, ≈ 2 мин).

## 7. Ограничения

* Только Незер, vanilla-арифметика ≥ 1.18; Overworld (Xoroshiro) этим методом не берётся (`docs/12` §1.4). Допуска ошибок нет (как у оригинала): блок, заменённый игроком/структурой/фичей, или опечатка ломают результат.
* Результат — 48 бит; 64-битный world seed — `--world-seed` (только «случайные» seed) или `crack-lift64`. «Близнецы» по бедроку неразличимы. При малой информации — отказ (код 4) либо множество кандидатов (`--force --max-cand`).
* Режим Paper проверен только на примере оригинала. Ядро под sm_89 (`ARCH=`); без CUDA — `make cpu` (медленнее оригинала по CPU-времени).
* Не сделано: очередь выживших в shared memory (оценка выигрыша ≈ 1.3–1.5× к 0.157 с; отвергнуто как несоразмерно сложное). Инструмента нет в `crack/Makefile` (свой `Makefile` в `crack/src/nether_bedrock/`, вывод в `crack/bin/`).
